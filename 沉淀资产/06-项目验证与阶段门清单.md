# 项目验证与阶段门清单

## 一句话结论

《网约车物语》的完成标准不是“页面能打开”,而是每次改动都有对应证据:构建能跑、页面能用、关键路径没坏、数据能写、AI 输出可控。

这份清单把“做完了”拆成不同类型的验证证据。

## 改动类型与证据要求

| 改动类型 | 例子 | 必须证据 | 建议证据 |
|---|---|---|---|
| 逻辑改动 | 派单、事件、结局、失败判定 | 构建通过、关键路径测试 | reducer 或策略模拟 |
| 数值改动 | 订单价格、培训费用、任务奖励 | 数据文件 diff、基础模拟 | 资源流报告 |
| UI 改动 | 三栏布局、弹窗、HUD | 浏览器打开、console 无错 | 多视口截图 |
| 文案改动 | 事件、司机、结局、AI 复盘 | 玩家可见性检查 | 文案长度和展示截图 |
| 日志改动 | telemetry、run record | JSONL 写入验证 | session/run 聚合样本 |
| AI 输出改动 | Prompt、schema、兜底 | schema 验证、异常输出兜底 | 示例 payload 回放 |
| 部署改动 | nginx、路径、资源引用 | 线上 URL 可访问 | API、榜单、静态资源检查 |

## 本项目最小验证链

每次实质性改动后至少执行:

1. 按影响范围运行构建脚本。
2. 启动本地服务。
3. 打开主入口页面。
4. 检查 console error。
5. 验证被改动功能的主路径。
6. 如果涉及 API 或日志,验证文件写入。
7. 如果涉及 UI,检查桌面和移动端至少一个关键视口。

## 阶段门模型

| 阶段 | 通过标准 | 本项目证据 |
|---|---|---|
| 概念 | 题材、核心体验、非目标清楚 | `PRODUCT.md` / `GAME_DESIGN.md` |
| 设计 | 主要机制有规则、公式、边界 | `GAME_DESIGN.md` |
| 架构 | 维护入口和构建产物关系清楚 | `AGENTS.md` / `src/` / `dist/` |
| 原型 | 核心循环可玩 | 主入口网页 |
| 生产 | 功能按分层迭代,改完可验证 | 构建脚本 + smoke server |
| 打磨 | UX、数值、文案有证据支撑 | Playwright 截图 / telemetry |
| 对外分享 | 方法、角色、Prompt 可复用 | `沉淀资产/` |

## 阶段门判断格式

每次要推进一个阶段或做一次大改版,可以用这个格式:

```markdown
## 阶段门检查

### 当前阶段

### 想进入的下一阶段

### 已有证据

| 证据 | 文件或结果 | 是否通过 |
|---|---|---|

### 阻塞项

### 可接受风险

### 结论

PASS / CONCERNS / FAIL
```

## 回归范围控制

不要每次都全量测试。按改动范围决定回归:

| 改动范围 | 回归范围 |
|---|---|
| 单个文案 | 对应弹窗或展示区域 |
| 单个 CSS 文件 | 相关组件 + 多视口 |
| 单个 React 组件 | 该组件入口 + 相邻状态 |
| 引擎逻辑 | 对应 action + 日结/月结/结局 |
| 数据结构 | 游戏页 + admin.html |
| 服务/API | smoke server + 真实写入文件 |

## 失败处理

验证失败时按顺序处理:

1. 先保留失败日志,不要直接改第二处。
2. 判断失败属于构建、运行、视觉、逻辑、数据还是服务。
3. 缩小到最小复现场景。
4. 只改最小必要文件。
5. 重新跑同一条验证。
6. 连续失败时升级到更深层调试,不要反复猜。

## 可分享的关键观点

对外分享时可以强调:

- AI 项目不是“生成完就结束”,而是要建立可重复验证链。
- 前端小游戏也应该有阶段门,只是阶段门可以很轻。
- 测试不一定都自动化,但证据必须明确。
- UI、文案、日志、AI 输出都需要不同类型的验收标准。
