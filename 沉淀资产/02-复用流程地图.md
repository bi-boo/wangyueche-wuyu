# AI 协同开发复用流程地图

## 总流程

```text
口头想法
  -> 产品文档
  -> 玩法/业务机制
  -> 分层实现
  -> 自动验证
  -> 上线或试运行
  -> 行为日志
  -> AI 复盘
  -> Skill / Agent / Prompt 沉淀
```

## 阶段拆解

| 阶段 | 输入 | AI 做什么 | 人做什么 | 产出 | 可复用资产 |
|---|---|---|---|---|---|
| 目标定义 | 一段口头需求 | 整理成目标、边界、用户路径 | 判断哪些才是核心问题 | 产品说明和机制框架 | Prompt |
| 机制设计 | 游戏规则、业务规则 | 写规则文档、补边界场景 | 判断取舍和复杂度 | `GAME_DESIGN.md` 类文档 | Skill |
| 方法论沉淀 | 项目经验、外部方法、失败教训 | 提炼 Pillars、GDD、阶段门、角色路由 | 判断哪些适合对外分享 | 方法论资产 | 文档 |
| 分层实现 | 文档和现有代码 | 按 data/engine/app/styles 修改 | 控制范围,确认体验方向 | 可运行功能 | Skill |
| 体验打磨 | 截图、反馈、游玩感受 | 改文案、弹窗、引导、布局 | 判断是否符合用户理解 | 更清晰 UI | Agent |
| 数值验证 | 策略和目标节奏 | 跑模拟、看资金/口碑/流失曲线 | 判断是否符合设计意图 | 策略模拟报告 | Agent |
| 回归验证 | 本地服务和测试入口 | 跑 smoke、查 console、验证 API | 确认验收标准 | 证据日志 | Skill |
| 数据采集 | 关键行为和状态 | 设计匿名事件、写 JSONL | 判断隐私和分析粒度 | telemetry 日志 | Skill |
| AI 复盘 | 行为日志和决策记录 | 聚合 payload、输出结构化评价 | 判断评价是否可信 | AI 复盘结果 | Prompt |
| 资产沉淀 | 项目经验 | 整理 Skill/Agent/Prompt | 判断哪些值得复用 | 资产包 | 文档 |

## 跨团队复用方式

### 适合复用的项目

- 内部运营工具
- 前端原型
- 培训演练工具
- 数据采集型活动页
- 需要 AI 总结用户行为的流程产品
- 需要长期迭代但人力很少的小产品

### 不建议直接复用的部分

- 游戏具体数值
- 网约车题材文案
- 本项目的目录名和部署路径
- 特定模型供应商配置

### 应该抽象复用的部分

- 先文档后代码
- 生成产物不手改
- 改动按层路由
- 自动回归验证
- 匿名原始日志优先
- AI 输出必须结构化
- 失败时要有本地兜底
- 踩坑要写进项目规则

## 一人团队工作方式

| 传统多人团队角色 | 在本项目中的替代方式 |
|---|---|
| 产品经理 | 用户本人定义目标、体验和取舍 |
| 前端工程师 | AI 按项目规则实现 React/CSS/构建 |
| 游戏策划 | AI 辅助整理机制、任务、事件、数值表 |
| 测试工程师 | smoke-server + 浏览器验证 |
| 数据分析师 | telemetry 原始日志 + AI 按需分析 |
| 技术文档 | AI 每轮同步 `GAME_DESIGN.md` / `CLAUDE.md` |

核心不是“少一个岗位”,而是把这些职责拆成 AI 可以执行、用户可以判断的标准流程。
