# 玩家日志分析提示词模板

## Prompt 定位

这个 Prompt 用于把匿名 telemetry JSONL 转成产品体验洞察。它的任务不是泛泛总结“用户体验不好”,而是基于日志证据定位卡点、误解点、跳出信号和需要补采的字段。

核心原则:

- 只根据日志证据分析
- 按 session/run 聚合
- 不推断用户身份
- 不把单个个案当总体规律
- 输出可执行改进建议

## 使用场景

- 分析玩家为什么卡在某个任务
- 分析用户为什么退出或失败
- 判断某个引导、弹窗、入口是否有效
- 比较不同版本的用户路径
- 找出 telemetry 还缺哪些字段

## 不适用场景

- 没有日志数据
- 只有最终分数,没有路径
- 需要恢复个人身份
- 需要严肃归因到个人能力

## 输入组织

建议把输入分成四段:

```text
分析问题:
{{本次要回答的问题}}

版本范围:
{{版本号或时间范围}}

日志摘要:
{{按 session/run 聚合后的摘要}}

原始日志片段:
{{精选 JSONL 片段,保留 sessionId/runId/eventType/eventName/game/payload}}
```

## Prompt 正文

```text
你是一个产品体验分析助手。现在给你一批匿名用户行为日志,日志来自一个交互式产品或网页游戏。

请只根据日志证据分析,不要凭常识编造。

分析目标:
1. 找出用户最容易卡住的阶段。
2. 找出用户可能误解的机制或入口。
3. 找出失败、退出或长时间停留前的共同路径。
4. 给出可以落地的产品修改建议。
5. 说明当前日志还缺什么字段。

分析规则:
- 必须按 sessionId/runId 聚合路径,不要只看单条事件。
- 每个结论都要引用 sessionId/runId 或具体事件证据。
- 不要推断用户身份。
- 不要把单个个案当总体规律,除非样本中反复出现。
- 如果样本不足,明确写“样本不足,只能作为个案观察”。
- 不要输出 Markdown,只输出 JSON。

输出格式:
{
  "summary": "一句话结论",
  "sampleScope": {
    "sessions": 0,
    "runs": 0,
    "versionRange": "版本范围",
    "limitations": ["样本或字段限制"]
  },
  "frictionPoints": [
    {
      "stage": "卡点阶段",
      "severity": "high|medium|low",
      "evidence": ["日志证据 1", "日志证据 2"],
      "interpretation": "可能原因",
      "suggestion": "建议改法"
    }
  ],
  "dropoffSignals": [
    {
      "signal": "退出或流失信号",
      "evidence": ["证据"],
      "possibleCause": "可能原因"
    }
  ],
  "misunderstandings": [
    {
      "hypothesis": "用户可能误解什么",
      "evidence": ["证据"],
      "fix": "建议改法"
    }
  ],
  "missingTelemetry": ["建议补采字段"],
  "priorityFixes": ["优先改动 1", "优先改动 2", "优先改动 3"]
}
```

## 适合输入的数据

| 数据 | 用途 |
|---|---|
| `session_start` | 判断进入和样本范围 |
| `ui` | 判断入口点击和重复操作 |
| `action` | 判断关键系统动作 |
| `decision` | 判断用户主动选择 |
| `snapshot` | 判断卡点前后状态 |
| `session_end` | 判断退出原因和结尾状态 |
| `game_over` / `flow_end` | 判断失败或完成路径 |

## 卡点信号定义

| 信号 | 可能含义 |
|---|---|
| 同一入口重复点击 | 用户没看懂反馈或入口没有完成任务 |
| 长时间停留无推进 | 任务目标不清、资源不足或入口不可见 |
| 弹窗后退出 | 弹窗压力过高、信息过长或打断过强 |
| 失败前无自救动作 | 风险提示不明显或自救入口不可见 |
| 频繁开关商店/招募 | 价格、资源或配对关系不清 |
| 快速开始又退出 | 首屏或开局引导没有建立动机 |

## 示例输入片段

```text
分析问题:
为什么新手没有完成“组建第三车组”?

日志摘要:
- sessions: 18
- runs: 12
- version: V15.42
- 7 个 run 停在 m5_third_crew 超过 8 分钟

原始日志片段:
{"sessionId":"s1","runId":"r1","eventType":"ui","eventName":"open_shop_modal","game":{"day":10,"currentMissionId":"m5_third_crew"}}
{"sessionId":"s1","runId":"r1","eventType":"ui","eventName":"close_shop_modal","game":{"day":10,"funds":5800}}
```

## 输出校验

调用方应检查:

- 是否是 JSON
- 每个 friction point 是否有 evidence
- evidence 是否包含 session/run 或事件
- 是否存在无证据心理判断
- priorityFixes 是否可执行
- missingTelemetry 是否具体

## 失败处理

| 情况 | 处理 |
|---|---|
| 样本少 | 输出限制,不要做总体判断 |
| 版本混杂 | 按版本分组或标注限制 |
| 日志字段缺失 | 放入 `missingTelemetry` |
| JSON 过长 | 减少原始日志,保留聚合摘要 |
| 结论无证据 | 删除或降级为假设 |

## 可复用边界

可跨项目复用:

- session/run 聚合
- 卡点信号识别
- 证据化输出
- 补采字段建议

需要按项目替换:

- 阶段名和任务名
- 关键指标
- 事件类型
- 产品语境
