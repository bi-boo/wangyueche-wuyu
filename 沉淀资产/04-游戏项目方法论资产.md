# 游戏项目方法论资产

## 一句话结论

《网约车物语》的关键沉淀不是“AI 帮忙写了一个游戏”,而是把单人游戏项目拆成一套可复用的决策系统:先定义体验,再写规则,再分层实现,最后用证据验证。

这套方法适合一人团队、产品原型、培训演练、活动页小游戏和复杂前端交互项目。

## 方法论最小闭环

| 环节 | 要回答的问题 | 项目里的对应资产 |
|---|---|---|
| 核心体验 | 玩家为什么要玩这个东西 | `PRODUCT.md` / `GAME_DESIGN.md` |
| 设计约束 | 什么想法应该保留,什么应该砍掉 | Game Pillars / Anti-Pillars |
| 机制文档 | 规则、公式、边界、依赖是什么 | `GAME_DESIGN.md` |
| 分层实现 | 该改数据、引擎、组件还是样式 | `AGENTS.md` / `CLAUDE.md` |
| 验证证据 | 怎么证明改完没坏 | `scripts/smoke-server.mjs` / Playwright |
| 行为反馈 | 玩家真实怎么操作 | telemetry JSONL |
| 复盘沉淀 | 下一次怎么少踩坑 | `沉淀资产/` |

## 核心设计框架

### 1. `MDA` 框架

从玩家体验倒推机制:

| 层级 | 在《网约车物语》里的含义 |
|---|---|
| Aesthetics | 玩家感受到经营压力、小人物命运、解锁发现 |
| Dynamics | 玩家形成扩张、培训、保现金、冲结局等策略 |
| Mechanics | 订单、车辆、司机、培训、任务、事件、结局 |

用法:新增机制前先问“玩家应该感到什么”,再决定规则怎么写。

### 2. `SDT` 玩家动机

| 需求 | 本项目的判断问题 |
|---|---|
| 自主 | 玩家是否有真实选择,还是只能按引导走 |
| 胜任 | 玩家是否知道自己为什么变强或失败 |
| 关联 | 玩家是否记得司机、事件和结局背后的处境 |

用法:如果一个新机制不服务这三类需求中的任何一个,大概率应该砍掉或延后。

### 3. 心流曲线

经营游戏的难度不应该一路平,也不应该突然暴涨。更适合本项目的是“阶段性上坡 + 解锁喘息”:

| 阶段 | 玩家能力 | 挑战来源 | 设计重点 |
|---|---|---|---|
| 开局 | 少量司机和车 | 现金紧、订单少 | 教玩家看懂车组和任务 |
| 扩张 | 可买车、招募、培训 | 资金和口碑压力 | 让投入有明显回报 |
| 中后期 | 多车组、多订单 | 事件、监管、债务、结局条件 | 防止单一最优策略 |
| 结局 | 已形成经营路径 | 最终评价和复盘 | 让玩家理解自己这局做了什么 |

### 4. 玩家类型取舍

《网约车物语》优先服务三类玩家:

| 类型 | 项目里的价值 | 对应设计 |
|---|---|---|
| 成就型 | 想通关、收集、达成目标 | 阶段任务、结局、成就 |
| 探索型 | 想发现系统和事件 | 隐藏结局、事件链、不同策略 |
| 叙事型 | 想记住角色和处境 | 司机背景、事件文案、AI 复盘 |

不优先服务:强竞技、社交压制、开放世界沙盒。

## `Game Pillars` 写法

Pillar 不是口号,而是能帮你做取舍的判断句。

| 标准 | 不合格写法 | 合格写法 |
|---|---|---|
| 可证伪 | 游戏要好玩 | 一屏内完成主要经营判断 |
| 有约束 | 内容越丰富越好 | 不服务司机命运感的事件不加 |
| 可执行 | 要有经营感 | 每个经济投入都要能看到回报或代价 |
| 能拒绝 | 什么都可以试试 | 不做开放世界、不做社交、不做付费 |

适合《网约车物语》的 Pillar 草稿:

1. **紧凑经营**:主要判断必须在一屏内完成。
2. **小人物命运感**:司机、事件、结局要让玩家看到经营背后的处境。
3. **现实行业质感**:数值、压力、事件要来自网约车语境,不能变成抽象 RPG。

## GDD 8 节最小标准

每个重要机制至少要能回答 8 个问题:

| 章节 | 要回答的问题 | 本项目示例 |
|---|---|---|
| Overview | 这个机制是什么 | 订单系统负责生成收入和经营压力 |
| Player Fantasy | 玩家应该感受到什么 | 像在调度一支小车队 |
| Detailed Rules | 规则怎么运行 | 订单如何刷新、司机如何接单 |
| Formulas | 数学怎么算 | 收益、时间、口碑变化 |
| Edge Cases | 极端情况怎么处理 | 没车、没司机、现金为负 |
| Dependencies | 依赖哪些系统 | 司机、车辆、区域、任务 |
| Tuning Knobs | 哪些值可调 | 价格、收益、阈值、奖励 |
| Acceptance Criteria | 怎么算做好了 | 玩家能完成任务、策略不单一、页面无错 |

## 适合分享的表达口径

对外分享时,不要讲成“用了 AI 做游戏”。更准确的说法是:

1. 用 AI 把产品想法拆成规则、代码、验证和复盘。
2. 用文档约束 AI,避免每轮都从头理解项目。
3. 用自动验证证明改动结果,避免只看“能打开”。
4. 用匿名日志和结构化复盘让项目持续学习。
5. 最后把过程沉淀成 Skill、Agent、Prompt 和方法论文档。

## 可复用边界

适合复用:

- 一人团队开发复杂原型
- 产品经理主导的互动 Demo
- 内部培训和演练工具
- 需要日志和 AI 复盘的轻量产品
- 需要长期迭代但工程人力少的前端项目

不建议直接复用:

- 大型商业游戏完整流程
- 强联网竞技项目
- 重资产 3D 美术生产
- 需要正式发行、合规、客服和运营团队的项目
