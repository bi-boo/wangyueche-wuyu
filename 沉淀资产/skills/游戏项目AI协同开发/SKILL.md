# 游戏项目 AI 协同开发

## Skill 定位

这个 Skill 用来约束 AI 在复杂前端游戏或交互式原型中的协作方式。它的目标不是让 AI 直接“想到哪改到哪”,而是让 AI 先理解产品规则、代码分层、构建边界和验证链路,再做最小必要修改。

适合一人团队、小团队原型、内部工具、网页游戏、活动页和需要持续迭代的前端产品。

## 适用场景

- 修改玩法、任务、事件、结局、失败条件
- 调整订单、价格、奖励、阈值、训练成本等数值
- 修改 React/Vue/HTML 组件行为
- 修改 CSS、响应式、一屏化、弹窗、引导、地图或面板布局
- 修改本地服务、AI 复盘、榜单、日志或部署入口
- 需要把单文件原型拆成可维护结构
- 需要判断构建产物和源文件是否同步

## 不适用场景

- 只需要写一段普通文案
- 只需要做行为日志分析,应使用“玩家行为日志与 AI 复盘”Skill
- 只需要做页面/API 验证,应使用“前端游戏回归验证”Skill
- 用户明确只要概念 brainstorm,不希望改文件

## 必须先读取的材料

| 材料 | 目的 |
|---|---|
| 项目约定文档 | 确认目录、构建、验证和禁止事项 |
| 产品/玩法设计文档 | 理解机制目标和用户体验 |
| 当前 Git 状态 | 避免覆盖用户已有修改 |
| 相关源文件 | 只对已经读过的文件下结论 |
| 构建脚本和验证脚本 | 明确完成后的验证方式 |

## 分层判断

改动前必须先判断任务属于哪一层:

| 改动类型 | 应改位置 | 注意事项 |
|---|---|---|
| 数值调整 | 数据配置 | 不改引擎逻辑 |
| 玩法逻辑 | 引擎或业务逻辑 | 同步设计文档 |
| 组件行为 | 前端组件 | 检查调用链 |
| 视觉样式 | 样式文件 | 检查多视口 |
| AI 输出 | Prompt、schema、解析、兜底 | 不直接信任模型原文 |
| 日志和数据 | telemetry、server、JSONL | 检查隐私边界 |
| 部署入口 | 服务脚本、部署文档 | 检查环境变量和路径 |
| 生成产物 | 不手改 | 只通过构建脚本生成 |

## 工作流程

1. 明确用户目标和验收标准。
2. 读取项目约定、设计文档和相关代码。
3. 判断改动层级,声明假设。
4. 如果涉及玩法或业务规则,先更新设计文档。
5. 修改对应源文件,避免无关重构。
6. 如涉及数据结构,同步后台工具或 schema。
7. 运行必要构建脚本。
8. 运行最小验证:
   - 构建
   - smoke test
   - 浏览器 console
   - API 写入
   - 多视口检查
9. 输出改动说明、验证证据和剩余风险。

## 决策原则

- 先保持系统可维护,再追求视觉或玩法扩展。
- 能改数据就不改逻辑。
- 能复用现有组件就不新造一套。
- 能用现有验证脚本就不靠手动感觉。
- 不把生成产物当维护入口。
- 不把内部字段直接变成用户文案。
- 不把 AI 输出直接展示到界面,必须结构化和兜底。

## 验证要求

| 改动 | 最低验证 |
|---|---|
| 数据/玩法 | 构建 + 关键路径模拟或 smoke |
| 组件/UI | 构建 + 浏览器打开 + console 检查 |
| CSS/布局 | 构建 + 多视口检查 |
| API/server | `node --check` + smoke/API 请求 |
| AI 复盘 | schema 校验 + 失败兜底 |
| telemetry | endpoint 写入 + JSONL 记录检查 |

没有完成验证时,输出必须明确写“未验证”。

## 输出模板

```text
## 本次改动

- ...

## 为什么这么做

- ...

## 修改范围

- 文件:
- 层级:

## 验证证据

- ...

## 剩余风险

- ...
```

## 失败处理

- 构建失败:先定位语法、依赖、路径或构建产物问题。
- 浏览器报错:查 console/pageerror/request failure,不要只看截图。
- 文档和代码冲突:以真实代码和运行结果为准,再修正文档。
- 连续修复失败:缩小范围,分离最小复现,不要继续盲改。
- 发现用户已有修改:保留并绕开,不要回滚。

## 可复用边界

可跨项目复用:

- 分层判断
- 文档先行
- 生成产物不手改
- 验证证据化
- AI 输出结构化

需要按项目替换:

- 目录结构
- 构建命令
- smoke test
- 设计文档名称
- 部署路径和环境变量
