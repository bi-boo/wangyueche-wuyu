# 可复用系统提示词逻辑

## 核心原则

这个项目最值得复用的系统提示词逻辑是:先让 AI 遵守项目事实,再让 AI 发挥能力。

如果没有这些规则,AI 很容易直接写代码、改错文件、忘记构建、忽略验证、把内部字段展示给用户。规则的价值是把 AI 的自由度限制在正确边界内。

## 规则 1:改动先判断层级

| 改动类型 | 应该改哪里 | 为什么 |
|---|---|---|
| 数值调整 | `wycwy-data.js` | 数据和逻辑分开,避免改引擎 |
| 逻辑变化 | `src/engine/*.js` | 派单、死亡、结局等属于引擎 |
| React 组件 | `src/app/*.jsx` | UI 行为在组件层 |
| 视觉样式 | `src/styles/*.css` | 样式独立维护 |
| 构建产物 | 不手改 `dist` / `wycwy-engine.js` | 由脚本生成,手改会丢 |

可迁移规则:

```text
做代码修改前,先判断改动属于数据、业务逻辑、组件、样式、构建产物还是部署配置。只改对应层,不要跨层乱动。
```

## 规则 2:玩法或业务规则先写文档

本项目约定 gameplay 改动先同步 `GAME_DESIGN.md`,再改代码。

可迁移规则:

```text
涉及业务规则、产品机制、用户流程变化时,先更新设计文档中的对应章节,再修改实现。完成后检查文档和代码是否一致。
```

这条规则对 AI 很重要,因为 AI 只改代码会导致团队后来不知道真实规则是什么。

## 规则 3:生成产物不能手改

本项目的 `wycwy-engine.js` 和 `dist/` 都是生成产物。

可迁移规则:

```text
识别 generated artifacts。维护源文件,运行构建脚本生成产物,不要直接手改生成文件。
```

## 规则 4:完成前必须给证据

本项目把完成标准从“代码改了”提升为“代码改了并且验证通过”。

可迁移规则:

```text
声明完成前必须给出验证证据:构建结果、smoke test、浏览器 console、截图或关键日志。不能只说已经修好。
```

## 规则 5:AI 输出进 UI 前必须结构化和兜底

AI 运营复盘要求模型输出固定 JSON,服务端还会清洗、解析和兜底。

可迁移规则:

```text
任何要展示给用户的 AI 输出,必须定义字段、长度、证据要求和失败兜底。不要把模型原文直接塞进界面。
```

## 规则 6:区分内部逻辑和用户可见文案

事件系统里 `keepBest`、`loseBest`、`markKeyDriver` 一类字段只服务内部结算,不能直接翻译成玩家文案。

可迁移规则:

```text
内部字段不等于用户文案。展示给用户前,必须判断这个字段是业务逻辑、诊断信息还是用户可见效果。
```

## 规则 7:原始日志优先,分析按需触发

本项目的 telemetry 先记录原始行为和 session summary,没有一开始固化复杂看板。

可迁移规则:

```text
早期产品先沉淀匿名原始日志,后续按具体问题用 AI 分析。不要在问题还没出现前做一套重型指标系统。
```

## 可直接放入其他项目 AGENTS.md 的简版

```text
涉及业务规则变化时,先更新设计文档,再改代码。
改动前判断所属层级:数据、业务逻辑、组件、样式、部署配置或生成产物。
生成产物不手改,只改源文件并运行构建脚本。
完成前必须提供构建、测试、浏览器或日志验证证据。
AI 输出进入 UI 前必须结构化、清洗、限制长度,并提供失败兜底。
内部状态字段不自动转成用户文案,只展示用户能理解且真实可见的效果。
早期数据分析优先沉淀匿名原始日志,按问题触发 AI 分析。
```
