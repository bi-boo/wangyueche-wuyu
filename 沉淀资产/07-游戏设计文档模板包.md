# 游戏设计文档模板包

## 一句话结论

这个模板包不是为了把项目文档做厚,而是为了让每个关键设计都有“为什么做、怎么运行、怎么验证”的最小结构。

《网约车物语》适合用轻量模板,不需要照搬大型游戏团队的完整文档体系。

## 模板 1: Game Pillars

适用:项目方向不清、功能越加越多、每次取舍都靠感觉。

```markdown
# Game Pillars

## 核心体验

玩家应该获得什么体验:

## Pillars

| Pillar | 一句话定义 | 设计测试 | 违反它的例子 |
|---|---|---|---|
| 紧凑经营 | 主要判断必须在一屏内完成 | 这个功能会不会让玩家离开主流程 | 主界面出现页面级滚动 |
| 小人物命运感 | 经营结果要能落到司机和事件上 | 这个事件是否让玩家记住人 | 只有数值没有处境 |
| 现实行业质感 | 压力来自网约车语境 | 这个设定是否像行业问题 | 变成抽象 RPG 加成 |

## Anti-Pillars

| Anti-Pillar | 为什么不做 |
|---|---|
| 不做开放世界 | 保持阶段化经营节奏 |
| 不做社交竞技 | 项目定位是单机模拟经营 |
| 不做付费系统 | 作品展示,不商用 |
```

## 模板 2: 机制 GDD

适用:新增系统、任务链、事件链、结局、训练、车辆、区域等核心规则。

```markdown
# 机制名称

## Overview

这个机制是什么,解决什么问题。

## Player Fantasy

玩家操作这个机制时应该感到什么。

## Detailed Rules

1. 规则一。
2. 规则二。
3. 规则三。

## Formulas

| 公式 | 变量 | 来源 | 说明 |
|---|---|---|---|

## Edge Cases

| 场景 | 处理方式 | 理由 |
|---|---|---|

## Dependencies

| 依赖系统 | 关系 |
|---|---|

## Tuning Knobs

| 参数 | 当前值 | 安全范围 | 调高影响 | 调低影响 |
|---|---|---|---|---|

## Acceptance Criteria

- [ ] 玩家能理解这个机制的入口。
- [ ] 正常路径能完成。
- [ ] 极端路径不会崩。
- [ ] 文档和数据字段一致。
```

|---|---|---|---|

| 消耗 | 数值 | 频率 | 目的 |
|---|---|---|---|

## Balance Targets

| 指标 | 目标 | 理由 |
|---|---|---|
| 第一辆车回本时间 |  |  |
| 第一次培训可感知收益 |  |  |
| 前期现金安全垫 |  |  |

## 使用原则

1. 不为模板而模板。只在有真实决策或真实验证时写。
2. 小改动用轻量模板,大机制才写完整 GDD。
3. 文档要链接到真实代码、数据或验证证据。
4. 模板字段可以删减,但不能删掉“目标、规则、证据”三类信息。
