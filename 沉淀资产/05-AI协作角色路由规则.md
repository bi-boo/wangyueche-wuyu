# AI 协作角色路由规则

## 一句话结论

AI 协作不是“一个助手什么都做”,而是把任务拆成不同职责:有人负责取舍,有人负责实现,有人负责验证,有人负责复盘。

《网约车物语》的资产沉淀里,Agent 的价值就是让 AI 在正确的职责边界内工作。

## 本项目角色分层

| 层级 | 角色 | 解决的问题 |
|---|---|---|
| 产品判断层 | 用户本人 | 定义目标、体验、取舍、最终判断 |
| 设计审查层 | 游戏设计 Agent / 经济系统平衡 Agent / 叙事文案 Agent | 判断机制、数值、故事是否值得做 |
| 工程健康层 | 架构巡检 Agent | 判断代码分层、构建链、文档事实是否健康 |
| 体验验证层 | 一屏化 UX 审查 Agent / QA 测试用例 Agent | 判断页面是否可用、测试是否可执行 |
| 数据复盘层 | 玩家日志洞察 Agent / AI 复盘守门 Agent | 判断真实行为和模型输出是否可信 |

## 角色路由表

| 用户问题 | 优先调用角色 | 典型输出 |
|---|---|---|
| 这个机制该不该加 | 游戏设计 Agent | 取舍理由、边界、验收标准 |
| 这个数值是不是太难 | 经济系统平衡 Agent 或玩法数值模拟 Agent | 资源流、策略模拟、调参建议 |
| 页面是不是太挤 | 一屏化 UX 审查 Agent | 信息层级、布局风险、多视口检查 |
| 事件文案能不能这么写 | 叙事文案 Agent | 玩家可见文案、内部字段过滤 |
| 改完怎么测 | QA 测试用例 Agent | 测试步骤、预期结果、通过标准 |
| 项目是不是被改乱了 | 架构巡检 Agent | 架构健康度、构建链、文档漂移 |
| 玩家为什么卡住 | 玩家日志洞察 Agent | session/run 路径、卡点、补采建议 |
| AI 复盘能不能展示 | AI 复盘守门 Agent | schema 检查、证据一致性、兜底 |

## 并行协作规则

当多个角色的输入互不依赖时,可以并行做判断:

| 场景 | 并行角色 |
|---|---|
| 修 bug | QA 测试用例 Agent 查复现路径;架构巡检 Agent 查调用链 |
| 调数值 | 经济系统平衡 Agent 查资源流;玩法数值模拟 Agent 跑策略 |
| 改主界面 | 一屏化 UX 审查 Agent 看布局;游戏设计 Agent 看信息是否必要 |
| 新事件链 | 叙事文案 Agent 看故事;游戏设计 Agent 看机制;AI 复盘守门 Agent 看展示边界 |

并行的前提:

- A 的输出不是 B 的输入
- 两个角色不会同时修改同一份文件
- 最终由用户或主 Agent 汇总取舍
- 有冲突时先停下来解释冲突,不要各改各的

## 冲突处理规则

| 冲突类型 | 处理方式 |
|---|---|
| 设计想做,UX 觉得放不下 | 先保一屏化主流程,再改成抽屉、弹窗或延后 |
| 数值合理,叙事不合理 | 保留数值目标,重写文案和事件设定 |
| 文档这么写,代码不是这么跑 | 以真实代码和验证结果为准,再修文档 |
| AI 输出好看但证据不足 | 不展示,交给 AI 复盘守门 Agent 做兜底 |
| 玩法有趣但范围太大 | 先写最小版本,把完整版本放后续 |

## 单人团队的简化模式

不需要每次都全量调用所有角色。按任务大小分三档:

| 任务规模 | 调用方式 |
|---|---|
| 小改动 | 主 Agent 直接处理,必要时只用 QA 测试用例 Agent 做验证 |
| 中等改动 | 设计/工程/验证三选二,例如游戏设计 + QA |
| 大改动 | 至少覆盖设计、工程、体验、验证四类判断 |

## 角色输出标准

每个 Agent 的输出都应该包含:

1. 当前判断结论。
2. 依据来自哪里。
3. 影响哪些文件或系统。
4. 有哪些风险。
5. 下一步该验证什么。

不合格输出:

- 只有“建议这么做”
- 没有证据来源
- 不说明影响范围
- 不区分确定事实和推测
- 不给验证方式

## 对外分享口径

可以把这套机制讲成:

> 一人团队不是让 AI 代替所有岗位,而是把多个岗位的判断方式拆成可复用 Agent。用户保留产品判断权,AI 负责结构化分析、实现和验证。

这比“我用了很多 Agent”更有分享价值,因为它说明了职责边界和协作方式。
