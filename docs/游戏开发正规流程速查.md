> 给「网约车物语」项目使用的游戏开发方法论速查。
> 这份文档只保留对本项目直接有用的设计、流程和资产沉淀方法。
> 它是项目内部参考,不是强制执行的项目规则。

## 一、游戏开发的"正规"是什么——心智模型

商业游戏工作室和你单人开发的根本差别，不在工具和代码，在**决策结构**：

| 业余/第一次做 | 正规工作室 |
|---|---|
| 边想边做，遇到问题再决定 | 先定核心承诺（Pillars），再让所有决策服从它 |
| 「这个机制好像不错就加上」 | 「这个机制服务哪个 Pillar？不服务就砍」 |
| 数值靠手感拍 | 每个公式有书面定义、有 tuning knobs、有边界用例 |
| 完成 = 看起来跑得起来 | 完成 = 有可验证证据（测试通过 / 截图 / 试玩报告） |
| 文档写完一次就过期 | 改机制前先改文档、再改代码 |

**核心心智**：游戏开发的混乱来源是「决策没有锚点」。正规流程的本质是**为每个决策建立一个可追溯的依据**——pillar → GDD → 公式 → 数值 → 实现 → 测试。

## 二、4 个必学的设计理论

这些理论是做机制评审、数值平衡和体验判断时的底层依据。第一次做游戏的人**最该补的就是这块**。

### 2.1 MDA 框架（Mechanics-Dynamics-Aesthetics）

学者 Hunicke、LeBlanc、Zubek 提出。从下往上看游戏：

| 层 | 是什么 | 你网约车的例子 |
|---|---|---|
| **Mechanics**（机制） | 你写在代码里的规则 | 司机派单算法、订单收益公式、死亡判定 |
| **Dynamics**（动态） | 玩家在玩的过程中产生的行为模式 | 玩家发现"先囤一批好司机再扩张"是最优解 |
| **Aesthetics**（美学体验） | 玩家最终感受到的情绪 | 「经营压力 + 见证小人物命运的唏嘘」 |

**关键洞察**：你设计的是 Mechanics，玩家体验到的是 Aesthetics，两者中间隔着 Dynamics——这就是为什么很多游戏「设计图很美但玩起来无聊」。

**MDA 的 8 种 Aesthetics**（你要先选 2-3 个作为目标）：
- **Sensation** 感官——视听满足
- **Fantasy** 幻想——扮演某种角色
- **Narrative** 叙事——故事推进的感动
- **Challenge** 挑战——技能掌握的成就
- **Fellowship** 社交——和别人一起玩
- **Discovery** 发现——挖掘秘密
- **Expression** 表达——展现自我
- **Submission** 沉浸——放松、冥想

**对你网约车的判断**：你大概率追求的是 **Challenge**（经营挑战）+ **Narrative**（小人物命运）+ **Discovery**（解锁结局/事件）。请你自己确认排序。

### 2.2 自我决定理论（Self-Determination Theory，SDT）

Deci 和 Ryan 提出的心理学理论，解释「为什么有些游戏让人玩不下去就难受」。玩家持续投入的根源是三个心理需求被满足：

| 需求 | 含义 | 网约车里的体现 |
|---|---|---|
| **Autonomy** 自主 | 玩家有真实选择权，不是按引导走流程 | 你能决定先扩车队还是先升司机？决定接监管还是赌一把？ |
| **Competence** 胜任 | 有清晰反馈，能看到自己变强 | KPI 涨了、解锁新车、达成阶段任务的反馈是否够明显？ |
| **Relatedness** 关联 | 与角色/世界产生情感联系 | 玩家会不会记住某个司机的故事？某个事件的选择？ |

**用法**：每次加新机制前问一句——这个机制服务三个需求中的哪一个？三个都不服务的机制基本可以砍。

### 2.3 Flow（心流）

心理学家 Csikszentmihalyi 的概念。玩家进入"忘记时间"的状态需要：**挑战难度刚好略高于当前技能水平**。

| 挑战 vs 技能 | 玩家状态 |
|---|---|
| 挑战 >> 技能 | 焦虑、放弃 |
| 挑战 ≈ 技能 | **心流**（理想） |
| 挑战 << 技能 | 无聊、放弃 |

**实操工具：难度曲线表**。把游戏拆成阶段，每个阶段标出"玩家此时拥有什么资源/能力"和"此时的挑战强度"。曲线应该是**阶梯式上升**（先给点喘息，再爬一坡）。

**对你网约车的判断**：阶段任务链就是难度曲线的载体。每章解锁的新机制（培训/改装/招募券）是技能成长，新订单类型/新事件是挑战增加。需要画一张表对照看是否平滑。

### 2.4 Bartle 玩家类型

学者 Richard Bartle 把玩家分四类，决定游戏吸引哪些人：

| 类型 | 动机 | 你网约车里如何吸引 |
|---|---|---|
| **Achievers** 成就型 | 通关、收集、KPI 达标 | 阶段任务、解锁全部结局、五星司机 |
| **Explorers** 探索型 | 挖掘机制、发现彩蛋 | 罕见事件链、隐藏结局、机制相互作用 |
| **Socializers** 社交型 | 和人产生连接 | 司机背景故事、NPC 对话 |
| **Killers** 杀手型 | 压制对手、竞争 | 单机经营游戏基本不服务这一类 |

**关键**：选 1-2 个主目标玩家类型，不要试图讨好所有人。**Killer 型不是你的目标用户，单机模拟经营无法服务他们**——这就是一个清晰的设计取舍。

## 三、Game Pillars——游戏的"宪法"

这是最实用的设计约束工具。它把“想做什么”转成后续每个取舍都能引用的依据。

### 什么是 Pillar

3-5 条**不可妥协的原则**，定义这个游戏的身份。所有设计、美术、音频、叙事、技术决策必须服务至少一条 Pillar。**不服务任何 Pillar 的功能不该存在**。

### 好 Pillar 的标准

| 标准 | 解释 |
|---|---|
| **可证伪** | "好玩"不是 Pillar，"战斗奖励忍耐而非进攻"才是——能被反对的才有约束力 |
| **有约束力** | 一条 Pillar 必须能让你对某些点子说「No」。从不让你拒绝任何东西的 Pillar 等于没有 |
| **跨部门** | 一条 Pillar 应该同时影响设计、美术、音频、叙事、工程，而不只是某个领域 |
| **能背诵** | 团队（你）能不看文档背出所有 Pillar。背不出的 Pillar 太多或太复杂 |

### 真实 AAA Pillar 案例（学习用）

| 游戏 | Pillar | 关键约束 |
|---|---|---|
| **God of War (2018)** | 父子情感旅程；连续镜头不切；北欧神话重新诠释 | 「连续镜头」彻底砍掉了游戏标准的电影化运镜手段 |
| **Hades** | 流畅快节奏战斗；通过重复推进剧情；每次 run 都教点新东西 | 「通过重复推进剧情」让 roguelike 的死亡变成叙事手段 |
| **Celeste** | 苛刻但公平；无门槛包容性；故事和机制是同一件事 | 「故事和机制是同一件事」——攀爬就是挣扎，dash 就是焦虑 |
| **Hollow Knight** | 氛围胜过解释；自己挣得的精通；世界讲述自己的故事 | 没有教学、没有手把手——靠环境设计教玩家 |
| **Dead Cells** | 每件武器都可用；战斗是舞蹈；永久死亡赋予意义 | 「每件武器都可用」是极强约束，要求百件物品持续平衡 |

### Anti-Pillars（反 Pillar）

同样重要——明确**这个游戏不是什么**。每个「不」保护一个「是」。

好 Anti-Pillar 是「团队真的可能想做但被排除掉的事」。「不是赛车游戏」毫无价值；「不是开放世界游戏」才有意义（因为这是一个真实的诱惑）。

### 给「网约车物语」的 Pillar 草稿（仅供参考）

我从你的 GAME_DESIGN.md 和 PRODUCT.md 推断，你的 Pillar 可能是：

1. **致敬开罗的紧凑经营节奏** —— 一屏化、像素感、一局可控时长
2. **小人物命运感** —— 每个司机有名字、有背景、会消失
3. **数值的真实感** —— 不是抽象 RPG，是网约车这个特定行业的现实

Anti-Pillar 草稿：
- **不是开放世界沙盒** —— 严格阶段化推进
- **不追求美术质感** —— 像素 + 占位元素就够了
- **不做付费/社交** —— 单机、不发布、不商用

**建议**：给自己花 30 分钟正式写 3-4 条 Pillar，命名为 `design/game-pillars.md`，以后每次想加新功能先问「服务哪条 Pillar？」

## 四、GDD（Game Design Document）的 8 个必备章节

每个关键游戏机制都建议补齐这 8 节。**对照检查你的 GAME_DESIGN.md**：

| # | 章节 | 内容 | 你的现状 |
|---|---|---|---|
| 1 | **Overview** | 一段话总结这个机制是什么 | 部分章节有，但不统一 |
| 2 | **Player Fantasy** | 玩家应该感受到什么情绪？想体验什么？ | **缺失**——第一次做游戏最常缺的就是这块 |
| 3 | **Detailed Rules** | 无歧义的机制描述 | 大部分章节有 |
| 4 | **Formulas** | 所有数学公式定义清楚（变量+公式） | 部分有，部分藏在代码里 |
| 5 | **Edge Cases** | 异常情况怎么处理 | **多数缺失** |
| 6 | **Dependencies** | 这个机制依赖哪些其他机制 | 缺失 |
| 7 | **Tuning Knobs** | 哪些值是可调的（指向 wycwy-data.js 字段） | 缺失 |
| 8 | **Acceptance Criteria** | 这个机制怎么算"做完"了——可测试的成功条件 | **完全缺失** |

**关键洞察**：你的 GAME_DESIGN.md 已经很厚（112KB），但缺的是**结构化**——每个机制的 8 节都齐全，下次自己回头改的时候不会迷失。

**最容易补的两节**：
- **Player Fantasy** —— 给每个机制写一句"玩家此时应该感觉到 ___"
- **Acceptance Criteria** —— 写 3-5 条"如果做到这些就算完成"

## 五、7 阶段开发流程

游戏开发可以粗分七个阶段,**了解自己处于哪个阶段就知道下一步该做什么**：

| 阶段 | 主要产出 | 你网约车的位置 |
|---|---|---|
| **1. 概念（Concept）** | 一句话定位 + Pillar 草稿 | ✅ 已完成（致敬开罗） |
| **2. 设计（Design）** | GDD + Game Pillar + 系统索引 | 🟡 进行中（GAME_DESIGN.md 在但缺结构） |
| **3. 架构（Architecture）** | 技术决策 ADR + 控制清单 | 🟡 部分有（Babel 拆分、文件结构都已决定但未文档化） |
| **4. 原型（Prototype）** | 验证核心玩法的可玩版 | ✅ 已完成（V1-V14 多次迭代） |
| **5. 生产（Production）** | 按 Story 拆分逐项实现 | 🟢 你在这阶段 |
| **6. 打磨（Polish）** | 性能、视觉、音效、平衡 | 还没到 |
| **7. 发布（Release）** | 你不发布——可跳过 | N/A |

**对你的建议**：你目前最该补的是**阶段 2 的结构化** + **阶段 3 的 ADR**。原型已经稳了，正在做阶段 5。

## 六、第一次做游戏最容易踩的 3 个坑

### 坑 1：Scope Creep（范围蔓延）

**症状**：「这个事件好像也可以加」「再做个监管系统吧」「再加个分公司机制」……做着做着越来越大，最后烂尾。

**对策**：每次想加新东西前问三个问题：
1. 服务哪条 Game Pillar？不服务就砍
2. 删掉它会让核心体验差多少？差不多就砍
3. 有多少现有机制是「锦上添花但不必须」？砍掉它们

**可沉淀的配套 Skill**：`/scope-check`。

### 坑 2：缺乏可证伪的 Pillar

**症状**：被问"你这游戏在追求什么"时，答的是「好玩」「沉浸感」「有意思」——这些是无意义的回答。

**对策**：花一天写 3-4 条**可证伪**的 Pillar，明天再回看仍然觉得对，就敲定。

### 坑 3：数值靠手感

**症状**：每个数字都是「感觉差不多就这样」，半年后回来不知道为什么是这个值。

**对策**：每个公式有书面定义。`wycwy-data.js` 里每张表的 schema 应该在 GAME_DESIGN.md 里有对应说明（变量含义、范围、调整时该看什么指标）。

**可沉淀的配套 Skill**：`/balance-check`。

## 七、给「网约车物语」的具体行动建议

按优先级排：

### 第 1 步（推荐立刻做，30 分钟）：写 Game Pillars

新建文件 `design/game-pillars.md`（或 `GAME_PILLARS.md` 放根目录），3-4 条 Pillar + 3 条 Anti-Pillar。这是后续所有决策的锚。

### 第 2 步（每个机制 15 分钟）：补 GDD 8 节

不要重写 GAME_DESIGN.md，**只在已有章节里补缺的小节**：
- 给每个机制补一句 **Player Fantasy**
- 给每个机制写 3-5 条 **Acceptance Criteria**
- 把 **Tuning Knobs** 链接到 wycwy-data.js 的具体字段

### 第 3 步：试用一个 skill 看效果

挑 `/balance-check`（你 admin.html 有大量数值）或 `/scope-check`（你机制已经很多）试一次。如果效果稳定,再沉淀成项目自己的 Skill。

### 第 4 步：建立 ADR 习惯

新建 `docs/adr/` 目录，每次做架构决定时写一份。已经做的决定先补三个最重要的：
- ADR-001：为什么用 Babel 多 script 拆分而不是 Vite/Webpack
- ADR-002：为什么 wycwy-data.js 是单文件 JS 而不是 JSON
- ADR-003：为什么 admin.html 独立工具而不是嵌入主游戏

格式不用复杂,核心是记录“为什么这么选、放弃了什么、以后什么情况下要重评”。

## 八、适合沉淀成资产的角色

这 5 类角色已经整理进 `沉淀资产/agents/`,后续关键决策时可以按职责调用:

| 角色资产 | 使用场景 |
|---|---|
| `游戏设计Agent.md` | 整体游戏设计、机制取舍、任务节奏和范围控制 |
| `经济系统平衡Agent.md` | 订单、培训、车辆、招募、奖励等资源流和平衡判断 |
| `一屏化UX审查Agent.md` | 主界面一屏化、信息层级、交互路径和多视口可用性 |
| `叙事文案Agent.md` | 事件文案、司机背景、结局、玩家选项和故事节奏 |
| `QA测试用例Agent.md` | 测试用例、回归清单、smoke 验证和可判定验收标准 |

配套 Skill 可以按试用价值逐步沉淀:

1. `/balance-check` —— 检查 `wycwy-data.js` 的数值合理性
2. `/scope-check` —— 防止机制越加越多
3. `/playtest-report` —— 自己玩完后整理反馈
4. `/design-system` —— 给某个新系统写正式 GDD
5. `/retrospective` —— 阶段性复盘
6. `/quick-design` —— 小改动写迷你设计稿
