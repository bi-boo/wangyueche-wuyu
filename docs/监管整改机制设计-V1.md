# 监管整改机制设计 V1

## 设计目标

借鉴滴滴出行 2021 年被监管下架 2 个月的真实事件，给中后期玩家设置一道"教学型难度墙"。

核心目标：
- **第一次大概率破产**——让玩家在剧情冲击中亲身体会"风险管理"的代价
- **死得明白**——破产复盘把伏笔翻给玩家看，玩家归因到自己而非游戏不公
- **第二次能扛住**——三档教学曲线（B 借贷 → B 不借贷 → A 主动合规）层层递进

---

## 一、机制总览

监管整改是一次按**游戏绝对时间**触发的链式事件，分四个时点：

| 游戏时间 | 事件 | 玩家可操作 |
|---|---|---|
| **Day 30** | 第 1 次通知：行业协会合规倡议 | 仅信息提示，无选项 |
| **Day 60** | 第 2 次通知：监管部门约谈（**唯一决策点**） | A：启动合规专项 / B：聚焦扩张窗口期 |
| **Day 90** | 监管检查 / 整改公告 | A 玩家：50% 躲过 / 50% 轻罚<br>B 玩家：必触发整改 |
| **Day 150** | B 玩家整改期解除 | 恢复正常运营 |

**触发逻辑**：按游戏绝对时间触发，无任何前置条件。每局游戏走到第 30 天就一定会收到第 1 次通知。

## 二、A 选项规则：启动合规专项

| 项 | 数值 | 适用时段 | 备注 |
|---|---|---|---|
| 一次性启动费 | 当月营收 **40%** | Day 60 当天扣除 | 不可撤销 |
| **永久月合规支出（衰减）** | 见下表 | **Day 90 起** | 不可撤销 |
| 司机招募冷却 | 5 天 | **仅 Day 60-90** | 合规审查期 |
| 车辆购买冷却 | 5 天 | **仅 Day 60-90** | 合规审查期 |
| 监管检查结果 | 50% 完全躲过 / 50% 当月营收 **10%** 象征罚款 | Day 90 触发 | 即便复查不过也只象征性罚 |

### 合规衰减曲线

第一次合规建设投入最高，随着体系成熟成本递减，最终稳定在 10%：

| 月份（自合规起始日起） | 月支出 |
|---|---|
| 第 1 个月 | 当月营收 **25%** |
| 第 2 个月 | 当月营收 **20%** |
| 第 3 个月 | 当月营收 **15%** |
| 第 4 个月起永久 | 当月营收 **10%** |

**逻辑闭环**：玩家已经掏了重金做合规，监管来了即便发现细枝末节问题也只是象征性罚款。Day 60-90 的 5 天冷却限制对应"合规审查走流程"。

## 三、B 选项规则：聚焦扩张窗口期

| 项 | 数值 | 适用时段 | 备注 |
|---|---|---|---|
| 订单量加成 | **+25%** | Day 60-90（30 天） | buff |
| 单均利润加成 | **+15%** | Day 60-90（30 天） | buff |
| 可选贷款 | 当月营收 **100%**、利率 10% | Day 60 决策点 | 玩家自选是否借 |
| 立即罚款 | 当月营收 **100%** | Day 90 触发当天 | 一次性扣款 |
| 整改期禁运 | 订单残血 **20%**（仅存量用户） | Day 90-150（60 天） | 固定成本照扣 |
| **永久月合规支出（衰减）** | 同 A 选项的衰减表 | **Day 90 起** | 监管强制要求 |
| **整改期止损工具** | 卖车 / 裁员 | Day 90-150 内 | 复用现有车队管理界面 |

### 整改期止损（B 玩家专享）

整改期玩家可主动减少固定成本：
- **卖车**：复用现有"卖车"操作，按车辆当前估值回收资金
- **裁员**：复用现有"解雇司机"操作，需支付 1 个月遣散费

**关键设计**：止损工具不是新增功能，而是允许玩家在整改期使用现有的车队管理操作。这让 B 玩家有挣扎空间，但同时也意味着卖掉的车解禁后还得重新买回——本质是把杠杆"反向操作"，减损但损失永久化。

## 五、四次弹窗完整文案

### Day 30 第 1 次通知（氛围铺垫）

> **【行业新闻】行业协会发布合规倡议**
>
> 近日，中国互联网协会牵头发布《网约车行业自律公约》，倡议各平台主动加强司机背调、车辆审查、用户数据保护等合规建设。多家头部平台已发表声明积极响应。
>
> 业内分析人士认为，监管层面的新一轮规范化或将启动。
>
> [ 知道了 ]

**设计意图**：措辞模糊、像装饰性新闻。玩家第一次读基本会跳过；第二次读会立刻警觉。

### Day 60 第 2 次通知（**唯一决策点**）

> **【重大事件】监管部门约谈头部平台**
>
> 今日上午，国家网信办、交通部联合约谈包括你在内的多家头部网约车平台，要求"主动履行社会责任、加强合规建设、配合监管检查"。会议明确表示将于近期启动专项检查工作。
>
> 你的法务总监建议尽快做出决策。
>
> ---
>
> **┌─ A. 启动合规专项 ─────────────────────┐**
> **│** 立即投入当月营收 **40%** 用于司机背调、车辆年检、 **│**
> **│** 数据安全建设。Day 90 起每月持续投入合规支出，    **│**
> **│** 比例从 25% 起逐月衰减,稳定后为 10%（永久）。       **│**
> **│** 合规审查期间（30 天内），司机招募和车辆采购将进入 **│**
> **│** 5 天冷却。**长期、不可撤销。**                      **│**
> **└─────────────────────────────────────┘**
>
> **┌─ B. 聚焦扩张窗口期 ⭐ 法务建议 ──────────┐**
> **│** 当前正值行业景气高点，合规支出可暂缓。           **│**
> **│** 未来 30 天内：订单量 **+25%**、单均利润 **+15%**。 **│**
> **│** 如需加速扩张，可一次性贷款当月营收 **100%**       **│**
> **│** （年化利率 10%）。                              **│**
> **│** [ ] 同时申请扩张贷款                            **│**

**设计意图**：
- A 写明"长期、不可撤销"——心理压力最大化
- B 标"⭐ 法务建议"+ 全是正向数字——引诱玩家选 B
- 贷款做成 B 选项的二级勾选，让"贪上加贪"也是玩家自主决定

> **☠ 平台破产**
>

>
> **本局监管整改累计影响：**
>
> · 立即罚款：¥{X}
> · 60 天禁运期亏损：¥{Y}
> · 合规支出累计：¥{Z}
> · {如借贷} 贷款本息未还：¥{W}
> · **合计损失：¥{总计}**
>
> ─────────────────────────────────
>
> **关键决策回顾：**
>
> 你曾在 **Day 60** 选择 **"聚焦扩张窗口期"**，拒绝了主动合规建设方案。
>
> {如借贷} 你还在 Day 60 借入贷款 ¥{X}，放大了风险敞口。
>
> ─────────────────────────────────
>
> **回看时间线：**
>
> · Day 30：「行业协会合规倡议」是第一个信号
> · Day 60：「监管部门约谈」是最后的转向机会
> · Day 90：监管整改公告

## 七、抽象政策事件框架（为后续黑天鹅扩展预留）

虽然 V1 只实现监管整改一个事件，但代码结构按"政策事件框架"抽象，未来加疫情、油价、限号等事件可直接复用。

### 框架核心设计

```
POLICY_EVENTS（wycwy-data.js）
├─ id: 政策事件标识（如 'gov_ban'、'epidemic'、'oil_crisis'）
├─ schedule: 时间表，按游戏绝对天数触发各阶段
│   └─ [{ atDay, stage, type: 'notice' | 'decision' | 'verdict' | 'resume' }]
└─ stages: 各阶段数据（弹窗文案、选项、效果）
    └─ { [stageId]: { title, desc, options, effects } }

policyState（state 字段，每个政策事件独立追踪）
├─ govBan: { decision, loanTaken, verdictResult, ... }
├─ epidemic: { ... }   ← 未来加
└─ oilCrisis: { ... }  ← 未来加

policyOngoingEffects（state 字段，统一汇总当前生效的政策影响）
├─ orderMultiplier: { value, untilDay, source }   ← 派单引擎读取
├─ recruitCooldownDays: { days, untilDay, source } ← 招募引擎读取
├─ vehicleCooldownDays: { days, untilDay, source } ← 购车引擎读取
└─ monthlyExpenses: [{ id, schedule[], startDay, source }]  ← 月报扣款
```

### 触发器：单一调度入口

```
function policyEventTick(state):
  for event in POLICY_EVENTS:
    for stage in event.schedule:
      if state.day == stage.atDay && !已触发(event.id, stage):
        触发对应阶段（弹窗 / 静默生效）
```

放在 `dayTick` 头部独立运行，与现有"按 7 天周期 + 抽签"的随机事件触发器完全隔离。

### 效果应用：插件式叠加

派单引擎、招募引擎、购车引擎、月结算只需要查询 `policyOngoingEffects`，不需要知道具体来自哪个政策事件。这样未来加"疫情→订单 -50%"、"油价上涨→单均利润 -10%" 时，只要往 `policyOngoingEffects` 里 push 一条记录即可，无需改派单逻辑。

### V1 只实现 GOV_BAN，但代码结构留出扩展位

V1 写代码时遵守这套抽象，但只填一个 GOV_BAN 配置。框架开销极小（几十行调度代码），换来的是后续每个政策事件只需新增数据条目。
